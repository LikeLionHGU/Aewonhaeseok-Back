§0 서비스 경계 먼저 읽을 것

백엔드는 두 프로세스로 나뉩니다. 매핑 엔진이 Python이라 JVM에서 직접 호출할 수 없기 때문입니다. 프론트는 스프링만 호출합니다. Python 서비스는 외부에 노출되지 않습니다.

스프링만 호출합니다. 사전을 메모리에 들고 있어 상태를 가집니다.

아래 각 엔드포인트에는 어느 쪽이 소유하는지 SPRING PYTHON 으로 표시했습니다. Python 소유 엔드포인트는 스프링이 그대로 중계하므로, 프론트가 보는 경로와 응답은 표에 적힌 그대로입니다.

왜 프로세스를 나누는가

Python 인터프리터를 매 요청마다 새로 띄우면 라이브러리 적재에만 약 1초가 붙습니다(실측). 서비스로 상주시키면 사전이 메모리에 남아 0.33초로 끝납니다. 배포도 컨테이너로 분리되어 스프링 호스트에 Python을 설치할 필요가 없습니다.

§1 공통 규약

요청·응답 모두 JSON입니다. 파일 업로드만 multipart/form-data를 씁니다. 시각은 전부 ISO 8601에 KST 오프셋을 붙입니다(2026-08-10T14:32:00+09:00). 응답 JSON의 한글은 이스케이프하지 않습니다.

JSON 키는 snake_case로 통일

Jackson의 기본값은 camelCase(autoMappedRate)라 그대로 두면 Python 서비스가 주는 auto_mapped_rate와 표기가 엇갈립니다. 스프링 설정에서 spring.jackson.property-naming-strategy=SNAKE_CASE를 켜서 양쪽과 프론트가 모두 같은 표기를 쓰게 합니다. 중계 구간에서 키를 변환하지 않아도 되므로 버그가 줄어듭니다.

에러 형식

모든 4xx·5xx는 같은 형태로 응답합니다. message는 화면에 그대로 띄울 수 있는 한국어 문장으로 주므로, 프론트가 문구를 새로 만들 필요가 없습니다.

B2 파일 접수 3 endpoints

원본 파일은 절대 수정하지 않고 그대로 보관합니다. 감사 대응 요구사항이므로 매핑 결과는 반드시 별도로 저장합니다.

POST /files 업로드 SPRING 잠정

multipart/form-data, 필드명 file. xlsx · xlsm · xls · csv만 허용합니다. 확장자가 다르면 400을 주고 저장하지 않습니다.

인코딩·헤더는 업로드 시점에 알 수 없습니다

encoding_detected와 header_row는 파일을 실제로 열어봐야 정해지므로 매핑을 실행한 뒤에 채워집니다. 업로드 직후 응답에는 이 두 필드가 없습니다(null인 필드는 응답에서 생략됩니다). 화면에서는 매핑 전까지 빈 값으로 두면 됩니다.

  "size_bytes": 148701,
  "content_type": "text/csv",
  "status": "uploaded",
  // encoding_detected · header_row 는 매핑 후에 생긴다
  "uploaded_at": "2026-08-09T14:32:00+09:00"

깨지기 쉬운 지점

엔진의 인코딩 폴백 순서는 utf-8-sig → cp949 → euc-kr입니다. 이 경로에는 아직 테스트가 하나도 없습니다. 엔진 테스트 픽스처가 전부 xlsx인데 실제 데이터는 전부 CSV이고, 공공기관 파일은 cp949가 태반입니다. 운영에서 가장 먼저 깨질 자리입니다.

B3 매핑 3 endpoints · 엔진 완성

매핑 엔진 자체는 구현과 테스트가 끝나 있습니다. 이 영역은 사실상 직렬화 작업입니다.

POST /files/{id}/mapping 매핑 실행 PYTHON 확정

요청 본문 없음. 동기 응답으로 처리합니다. 작업 큐를 두지 않습니다.

스프링은 이 요청을 받아 Python 매핑 서비스에 그대로 위임하고, 돌려받은 결과를 DB에 저장한 뒤 프론트에 전달합니다. 프론트 입장에서는 경로도 응답도 아래 그대로입니다.

실측 근거

사전 로딩 0.019초. 가장 큰 파일(9.08MB · 104만 행)의 매핑이 0.33초, 나머지 샘플은 전부 0.06초 이하였습니다. 비동기 큐를 만들면 코드가 두 배가 되고 프론트도 상태 폴링을 구현해야 하는데, 그럴 이유가 없습니다.

B4 용어 검증 핵심 차별점

이 영역의 절대 규칙

사용자 판정을 사전 CSV에 직접 쓰지 않습니다. 사전은 git으로도 관리되므로, CSV에 쓰면 다음 merge 때 사용자 판정이 전부 사라집니다.

엔진의 apply_review()는 사전 CSV를 직접 덮어쓰므로 웹에서 절대 호출하지 않습니다. CLI 전용입니다. 판정은 DB 테이블에만 적재합니다.

GET /reviews 검증 대기열 SPRING 잠정

쿼리 ?file_id=41&status=pending. needs_review와 unmapped만 나옵니다. 컬럼명만으로는 판단이 불가능하므로 실제 값 요약을 반드시 함께 줍니다.

status는 pending(기본, 미판정만) 또는 all입니다. candidate_name에 후보 코드의 한글 표준명이 함께 옵니다 — MD-006만 보여주면 사람이 판단할 수 없기 때문입니다.

{
  "items": [
    {
      "id": 88,
      "file_id": 41,
      "raw": "채수시각\n(WMCTM)",
      "mapping_status": "needs_review",
      "candidate_code": "MD-006",
      "candidate_name": "측정일자",
      "score": 80.0,
      "value_summary": {
        "row_count": 1980,
        "distinct_count": 24,
        "samples": ["09:30", "10:00", "10:30"],
        "all_unique": false
      },
      "verdict": null
    }

}
실제 함정 사례

위 채수시각은 후보 MD-006(측정일자)이 80점으로 나오지만, 정답은 MD-012(측정시각)입니다. 저장소의 홀드아웃 판정 가이드에 기록된 실제 사례입니다. 점수가 높다고 그대로 승인하면 안 된다는 것을 화면에서 사용자에게 알려줘야 합니다.

POST /reviews/{id}/verdict 판정 저장 SPRING 잠정 
// 요청
{
  "verdict": "MD-012",
  "note": "측정일자가 아니라 측정시각임",
  "reviewed_by": "박서연"
}
화면 버튼보낼 값
맞음"승인"
아님"기각"
다른 항목 선택"MD-012" — 고른 표준코드

판정 시각은 서버가 기록합니다. 판정자는 reviewed_by로 보내주세요 — 로그인이 없으므로 화면에서 이름을 입력받아야 합니다.

보내지 않으면 "미상"으로 저장됩니다. 판정 자체는 되지만 사전 이력이 그만큼 약해집니다.

// 200 OK
{
  "id": 88,
  "verdict": "MD-012",
  "reviewed_by": "박서연",
  "reviewed_at": "2026-08-09T14:32:00+09:00",
  "applied_to_dictionary": false
}

applied_to_dictionary는 항상 false로 시작합니다. 판정이 실제 사전에 반영되는 것은 팀이 CLI로 별도 처리하는 단계이고, 그때 true가 됩니다.

GET /standards 기준 세트 조회 SPRING 결정 필요

배출허용기준 · 하천 생활환경기준 등 세트 목록입니다. 현재 사전에는 기준치 숫자가 없습니다. 측정항목 사전 17개 컬럼 어디에도 없고 법령 조항 이름만 문자열로 들어 있어, 별표 13과 환경기준에서 숫자를 추출해 테이블을 새로 만들어야 합니다. B6 선행이 필요합니다.

B5 측정값 2 endpoints

원본은 가로형(컬럼마다 항목)이라 그대로는 질문에 답할 수 없습니다. 한 행에 하나의 측정값이 오도록 펴서 적재합니다. 펴는 일은 Python이 하고 스프링은 저장만 합니다.

POST /files/{id}/ingest 측정값 적재 SPRING 잠정

매핑이 먼저 끝나 있어야 합니다. 다시 실행하면 기존 값이 갱신됩니다 — 사전이 자란 뒤 재적재하는 것이 정상 흐름이기 때문입니다.

{
  "file_id": 7,
  "mapping_run_id": 7,
  "dictionary_version": "dict-2026-08-10",
  "source_rows": 96,
  "measured_columns": 7,
  "inserted_values": 672,
  "skipped_values": 0,
  "flagged_values": 0

skipped_values는 숫자로 바꿀 수 없던 값입니다(불검출, <0.001 등). 버리지 않고 원문을 함께 보관합니다. flagged_values는 품질 경고가 붙은 값입니다.

GET /measurements/summary 적재 결과 요약 SPRING 잠정

쿼리 ?file_id=7(선택). 전체 건수·항목별 통계·기준 초과 목록을 돌려줍니다. B7 자연어 분석이 붙기 전까지 데이터가 실제로 들어왔는지 확인하는 용도입니다.

초과 집계에서 원폐수를 뺀다

원폐수는 처리 전 물이라 배출허용기준을 넘는 것이 정상입니다. 방류수와 섞어 세면 위반 건수가 통째로 부풀려집니다 — 데모 데이터에서 240건이 15건으로 줄었습니다.

그런데 이 구분을 담을 표준 용어가 사전에 아직 없습니다(2026-08-11 확인). 지금은 원본 문자열(원폐수 / 방류수)로 받아 두었고, 사전에 등재되면 표준코드로 옮깁니다.

B6 기준치 3 endpoints

법령이 정한 배출허용기준입니다. 결과 화면의 기준선과 초과 판정이 여기에 달려 있습니다.

기준치는 항목당 하나가 아닙니다

별표 13은 지역구분(청정·가·나·특례) x 배출규모마다 값이 다릅니다. 같은 BOD라도 청정지역과 나지역의 기준이 다릅니다.

실측으로 확인된 차이입니다 — 같은 데이터에 청정지역 기준을 적용하면 초과 63건, 가지역이면 5건입니다. 조건 확인 화면에서 지역구분을 반드시 고르게 해야 합니다. 고르지 않으면 기준선을 표시하지 않습니다.

수소이온농도는 limit_min과 limit_max가 모두 있습니다. 5.8~8.6 범위라 아래로 벗어나도 위반입니다.

GET /standards 기준 세트 목록 SPRING 잠정

조건 확인 화면의 드롭다운을 채웁니다. unverified_count가 함께 오니 화면에 경고를 띄울 수 있습니다.

{
  "sets": [{ "standard_set": "배출허용기준", "item_count": 21,
             "legal_basis": "물환경보전법 시행규칙 별표 13", "source": "demo" }],
  "region_grades": ["가지역", "나지역", "청정지역"],
  "unverified_count": 21

지금 값은 법령 대조 전입니다

현재 적재된 기준치는 전부 source=demo입니다. 별표 13 원문과 대조하지 않았습니다. 실제 판정 근거나 발표 자료로 쓰면 안 됩니다. 원문을 확보해 옮겨 넣고 law로 바꿔야 합니다.

GET /standards/limits 기준치 목록 SPRING 잠정

쿼리 ?standard_set=배출허용기준&region_grade=가지역&item_code=WQ-005. 결과 화면이 그래프에 기준선을 그릴 때 씁니다. limit_min이 없는 항목은 응답에서 필드가 생략됩니다(상한만 있다는 뜻).

GET /standards/exceedances 기준 초과 목록 SPRING 잠정

적재된 측정값을 법령 기준치와 대조합니다. 성적서에 딸려 온 기준치가 아니라 법령 기준으로 판정하고, 둘이 어긋나면 limit_mismatch_count로 알려줍니다.

원폐수는 제외합니다. 처리 전 물이라 기준을 넘는 것이 정상이고, 섞어 세면 위반 건수가 부풀려집니다.

B7 분석 4 endpoints

조건을 받아 통계를 냅니다. 홈의 질문 입력, 조건 확인, 결과, 근거 상세 네 페이지가 이 영역을 씁니다.

사용자가 SQL을 보내지 않습니다

조건만 보내면 서버가 SQL을 조립합니다. 값은 전부 바인딩 파라미터로 들어가고, SQL 문법에 섞이는 것은 집계 단위와 지표뿐인데 그것도 열거형이라 임의 표현식이 들어올 수 없습니다. 주입 위험이 구조적으로 없습니다.

자연어 파싱이 나중에 붙어도 파서가 문장을 이 조건 객체로 바꿔 줄 뿐이라, 파서가 틀려도 이상한 SQL이 돌지는 않습니다.

사전은 서버 시작 시 1회만 메모리에 올라갑니다. upstream에서 사전을 merge해도 이 API를 부르기 전까지는 옛날 사전을 씁니다.

리로드 판단은 엔진의 내용 해시 비교가 처리합니다. 파일 수정 시각이 아니라 내용을 보므로, 같은 내용을 다시 내보내도 불필요한 리로드가 일어나지 않습니다. 사전 로딩이 0.019초라 별도 최적화도 필요 없습니다.

{ "reloaded": true, "from": "dict-2026-08-10", "to": "dict-2026-08-12" }

이미 최신이면 reloaded가 false로 옵니다.

§7 구현 순서

기능명세서의 개발 순서에는 B2 · B4 · B1이 빠져 있어 아래로 조정했습니다.

  1. B2 파일 접수인코딩 회귀 테스트를 먼저 작성합니다.
  2. B3 매핑 API엔진 래핑. 사실상 직렬화 작업입니다.
  3. B4 용어 검증 + 전후 비교핵심 차별점. 여기까지가 1차 데모입니다.
  4. B5 데이터 적재스키마 설계부터 시작합니다.
  5. B6 기준치법령에서 숫자 추출.
  6. B7 분석조건 선택 방식을 먼저, 자연어 파싱은 마지막에.

1번부터 3번까지가 끝나면 "제각각인 데이터를 넣으면 표준화되고, 애매한 것은 사람이 판정하며, 그 판정으로 사전이 성장한다"는 이야기가 완성됩니다. 심사에서 가장 강한 카드를 일찍 손에 쥐는 순서입니다.

§8 기술 전제

영역선택이유
본 서버Spring Boot · JPA계정 · 파일 · 판정 · 분석. 프론트가 호출하는 유일한 대상
매핑 서비스Python · FastAPI엔진이 Python(pandas · rapidfuzz)이라 JVM에서 직접 호출 불가. 컨테이너로 분리
데이터베이스MySQL 8반드시 utf8mb4. 3바이트 utf8은 ㎎/L·Cl⁻ 같은 표기에서 깨진다
파일 저장로컬 디스크초기 단계. 원본 보존 요구가 있으므로 경로와 해시를 DB에 기록
사전 저장소CSV (당분간)엔진이 CSV를 직접 읽는다. DB 이관은 검증 화면 완성 이후
MySQL로 가면서 알아둘 것

저장소에 준비된 사전 DB 스키마는 PostgreSQL 전용입니다. timestamptz 11곳, 스토어드 함수 5개, pg_trgm 유사도 인덱스, text[] 배열, ON CONFLICT 등이 그대로는 동작하지 않습니다. 대부분 기계적 변환이지만 trigram 유사도 검색만은 MySQL에 대응물이 없습니다.

다만 지금 단계에서는 영향이 없습니다. 엔진은 DB가 아니라 CSV에서 사전을 읽고, 유사도 매칭도 Python의 rapidfuzz가 합니다. 이 스키마는 사전을 DB로 옮기는 훗날을 위한 것이라, 그 시점에 포팅 작업을 한 번 잡아두면 됩니다.

TEXT 컬럼에 걸린 UNIQUE 인덱스가 4개 있습니다. MySQL은 길이 지정이 필요하므로 해당 컬럼을 VARCHAR(255)로 바꿉니다. 표준용어 표기가 그보다 길 일은 없습니다.
