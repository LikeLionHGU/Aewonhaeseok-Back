# 매핑 서비스 (Python)

컬럼명을 표준코드로 바꾸는 서비스. **스프링이 내부에서만 호출한다.** 외부에 노출하지 않는다.

## 왜 따로 떠 있나

매핑 엔진이 Python(pandas · rapidfuzz)이라 JVM에서 직접 부를 수 없다.

요청마다 파이썬을 새로 띄우는 방법도 있지만, 라이브러리 적재에만 **약 1초**가 붙는다(실측).
서비스로 상주시키면 사전이 메모리에 남아 **0.3초**로 끝난다.

```
프론트 ──▶ 스프링부트 :8080 ──내부──▶ 매핑 서비스 :8000
```

## 실행

의존성이 두 벌이다. 엔진 것과 서비스 것을 모두 설치한다.

```bash
python -m pip install -r ../../requirements.txt
python -m pip install -r requirements.txt
```

```bash
uvicorn app:app --port 8000
```

떴는지 확인:

```bash
curl http://localhost:8000/health
```

## 엔드포인트

| 메서드 | 경로 | 내용 |
|---|---|---|
| `POST` | `/map` | 파일 하나 매핑. multipart, 필드명 `file` |
| `POST` | `/map/column` | 컬럼명 하나만. `{"name": "총질소"}` |
| `GET` | `/dictionary/version` | 엔진의 `VERSION.json` 그대로 |
| `POST` | `/admin/reload-dictionary` | 사전 다시 읽기 |
| `GET` | `/health` | 기동·사전 적재 확인 |

## ⚠ 사전을 갱신했으면 리로드해야 한다

사전은 **서비스가 시작할 때 한 번만** 메모리에 올라간다.
저장소 루트에서 `git merge upstream/main`으로 CSV가 바뀌어도,
아래를 부르기 전까지는 옛날 사전을 계속 쓴다.

```bash
curl -X POST http://localhost:8000/admin/reload-dictionary
```

내용 해시로 판단하므로 같은 내용이면 `"reloaded": false`가 온다.

> 매핑률이 갑자기 이상해지면 이것부터 의심할 것.
> 온톨로지 인수인계 문서에 작성자가 같은 함정에 두 번 걸렸다고 기록돼 있다.

## 손대면 안 되는 것

`pipeline/`과 `ontology/`는 **upstream 저장소가 관리한다.** 여기서는 읽기만 한다.
고치면 다음 `git merge`에서 충돌이 나거나 수정이 덮어써진다.
엔진에 바꿀 것이 있으면 매핑 엔진 저장소에 반영을 요청한다.

인코딩 판별(`detect_encoding`)을 이 파일에서 다시 구현한 것도 같은 이유다.
엔진의 `read_data_file()`은 인코딩 폴백을 시도하지만 어느 것이 통했는지 돌려주지 않는데,
화면에 표시할 값이 필요해서 엔진을 고치는 대신 같은 순서로 여기서 판별한다.

## 응답에서 주의할 점

**`exact` 판정에는 `score`가 없다(`null`).** 사전에 정확히 있었다는 뜻이지
유사도 100점이 아니다. 화면에 "100점"으로 표시하면 안 된다.

**`value_summary`는 사람이 판정해야 하는 컬럼에만 붙는다.** 104만 행짜리 파일에서
전 컬럼의 고유값을 세면 느려지는데, 자동 확정된 컬럼에는 쓰이지도 않는다.

이 요약이 왜 필요한지는 실제 사례가 있다. `구분`이라는 같은 컬럼명이
인천 파일에서는 날짜(`2017-01-01`), 제주 파일에서는 분기(`1분기`)를 가리킨다.
컬럼명만 보여주면 사람도 판정할 수 없다.
